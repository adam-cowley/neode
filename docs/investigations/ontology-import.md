# Importing existing ontologies (graph schemas) into neode models

Investigation for [NTS-666](https://linear.app/neo4j/issue/NTS-666). Deliverable is a recommendation, not a feature.

## Recommendation

For 1.x, deepen the **existing** `generateModels()` introspector rather than adding a new import API: emit `unique: true` / `exists: true` for constraints whose names match neode's deterministic naming, so a fresh database bootstrapped from generated models keeps the guarantees the source graph had. Add the **Neo4j Ontology Graph Specification** (official, versioned, SDK-backed since 2026) as the second import source via a small pure mapper — that is the "import an ontology" ask properly served. Keep generation **one-shot scaffold-then-hand-maintain** with `schemaDrift()` as the verification loop; do not build RDF/OWL import, incoming-direction inference, writable-relationship emission, or live merge in 1.x.

The round-trip the introspector was designed for is real and integration-tested: generate → `defineModel()` each model → `installSchema()` → `schemaDiff()` reports no drift on the generated labels (`test/integration/schema-generate.test.ts`). This works because the generator deliberately re-declares no constraints or indexes — `installSchema()` creates nothing, so nothing can collide with the hand-installed schema under a second name.

## 2. What a user hand-corrects after generation

Fidelity audit of the current output, in rough order of pain:

1. **Relationships are read-only.** Every generated relationship is `relatedOne`/`relatedMany` (`@RelatedOne`/`@RelatedMany`) — read projections only. Writable relationship declarations (`OneToMany`/`relationships`) are app intent the introspector cannot guess, so every relationship a consumer writes must be hand-converted. Documented in the module header; correct as a default, but it is the largest single edit.
2. **Uniqueness is silently lost on a fresh database.** The unique-constraint property gets `primary: true` but never `unique: true` (they are independent flags in `PropertyDefinition`; `primary` only marks lookup/matching semantics, `unique` is what `installSchema()` backs with a constraint). Against the introspected database the round-trip stays drift-free because the constraint already exists — but a fresh database bootstrapped from the generated models gets **no** uniqueness constraint, and `merge()` races go unguarded. The same applies to range/fulltext/vector indexes and composite constraints: nothing is emitted, so a fresh DB is silently unconstrained.
3. **Every property is optional.** Sampling cannot prove NOT NULL — but on Enterprise, `SHOW CONSTRAINTS` lists `IS NOT NULL` (EXISTS) constraints, and the introspector reads `SHOW CONSTRAINTS` already; the information is dropped on the floor.
4. **Direction is always `out`, captured once from the source label.** A model never sees its incoming relationships; both ends of an association cannot be declared without hand-editing one side. `BOTH` is never emitted.
5. **Cardinality is noisy.** `many` is inferred from average out-degree within the sample (`count > sources`): one person with two movies in the sample makes the relationship "many". Write-path cardinality (`one`/`zeroOrOne`, NTS-161) is never emitted. More than 20 distinct `(type, target)` pairs per label are silently truncated (`RELATIONSHIP_LIMIT`).
6. **Type fidelity is lossy.** Integers and floats collapse to `number`; temporal and point properties render as `@Property({ type: 'datetime' }) createdAt?: unknown` — the declared type is right, the TS type is a hand-fix. On Enterprise, property-type constraints could disambiguate int vs float. Properties absent from every sampled node (sparse data) are missed entirely.
7. **No meanings.** `description` is never emitted — correctly, since sampling cannot invent semantics. This is exactly what an ontology source (below) carries and neode's `description` field can hold.

## 3. Sources, ranked

The issue asks what users actually have to import from. Ranked by 2026 reality:

1. **A live database with data but no models** — the dominant case, and already served (NTS-164/577). The remaining work is fidelity, not existence.
2. **A Neo4j Ontology Graph Specification document** — new since this issue was scoped: the [Ontology Graph Specification](https://neo4j.com/docs/ontology-graph-spec/) (v1.1.0) is Neo4j's official, versioned YAML/JSON format for graph models, with a published JSON Schema and a JS/TS SDK (`@neo4j/ontology-graph-spec`, Apache-2.0). Its shape maps almost 1:1 onto neode: `nodes` (label, description, properties with `type`/`unique`/`must_exist`), `relationships` (type, `from`/`to` — i.e. direction, edge properties), constraints and indexes. This is the honest meaning of "importing an existing ontology" for a property-graph OGM.
3. **RDF/OWL via neosemantics (n10s)** — deliberately last. `n10s.onto.import.*` loads an ontology as a _meta_-graph (`:Class`/`:Relationship`/`:Property` nodes with `SCO`/`DOMAIN`/`RANGE` edges); mapping that onto OGM models is an OWL-to-OGM modelling project of its own, and the issue's own guidance says not to start here without demand.
4. **Another OGM's definitions (Neogma, neode 0.x)** — low demand; hand-porting is a one-off per adopter. Neode 0.x schema files are nearly neode-ogm map schemas already (`SchemaDefinition` is documented as "neode parity"), so this source is close to free but also close to valueless.

## 4. Approaches compared

**(a) Deepen the introspect → generate round-trip.** Emit the constraint facts the introspector already reads but drops: `unique: true` when the installed uniqueness constraint's name matches `schemaObjectName(label, [key], UNIQUE)` (neode-managed naming), `exists: true` on Enterprise-detected EXISTS constraints, `index: true` under the same name guard. The name guard is load-bearing: a hand-named constraint must stay un-emitted, or `installSchema()` would try to create a second constraint over the same label+property and fail at apply time — the shadowing problem the generator was explicitly designed to avoid. With the guard, the fresh-DB bootstrap becomes constraint-complete _and_ the introspected-DB round-trip stays drift-free (the deterministic names still match). Small, contained in `generate.service.ts` + tests.

**(b) APOC/meta procedures vs SHOW-based introspection.** The comparable-tool precedent — `neomodel_inspect_database` — needs APOC (research/ogm-dream-feature-report.md, Tier 3 item 28, sized $M). neode's introspector deliberately does not: `CALL db.labels()`, `SHOW CONSTRAINTS` and bounded sampling work on Community, Aura, and the embedded Relate engine alike (the fake-provider unit tests exercise them without a server). APOC's `apoc.meta.*` would consolidate type/direction discovery into one call, at the cost of a plugin dependency, a broken Relate backend, and redundant information sampling already provides. Stay SHOW-based; treat APOC as a non-option for 1.x.

**(c) `importOntology()` API vs improving the CLI.** For the live-graph source, no new API is needed: `generateModels()` is already library-shaped (takes a `ConnectionProvider`, returns structured data); only the bin sits on top. For the Ontology Graph Spec source, the right shape is a small pure mapper `ontologySpecToSchemas(model: GraphModel): Record<string, SchemaDefinition>` in core — neode defines the mapping, while parsing/validation stays with the spec's own SDK (decode with `@neo4j/ontology-graph-spec`, pass the decoded model in). That keeps the dependency out of neode's runtime (a devDependency for tests), avoids hand-maintaining a parser against a versioned spec, and matches the house rule against importing dependencies for a few lines. A CLI flag on `neode-generate` can come later if demanded; the map-schema output composes with `withDirectory()` as-is.

**What comparable OGMs do.** The research report at the workspace root (`research/ogm-dream-feature-report.md`, not in-repo) is directly on point: item 28 lists "Model generation from an existing DB (`neomodel_inspect_database` precedent; needs APOC)" in **Tier 3 · LATER**, priced $M — a wish, not a near-term feature. Every tool that ships introspection ships it **one-shot**: neomodel's inspector scaffolds and exits, `@neo4j/graphql`'s `generate()` re-runs on schema change, Prisma `introspect` scaffolds and hands the file to the user. Nobody does live merge into existing definitions, and the report's cut list explains why: auto-DDL `synchronize: true`-style sync is "documented unsafe" (TypeORM), and generated diffs that drop-and-recreate are the most-thumbed-down ORM issue category (TypeORM #3357, 97 👍). Its anti-pattern 9 ("three ways to define a model" — MikroORM's decorators/`defineEntity`/`EntitySchema`, Neogma's two decorator flavours → "pick one") is also the argument for import emitting **only the two existing definition styles**, never a third format.

## 5. Merge semantics and target shape

- **One-shot, no merge.** Generation is a scaffold step at adoption time; after that the files are hand-maintained source and verified against the database with `schemaDrift()`. Re-running `neode-generate` overwrites — matching neomodel, Prisma, and `@neo4j/graphql`, and the research report's auto-DDL verdict. Neither `skip`/`error`/`merge` option bags nor a diff-and-patch generator are justified for 1.x.
- **Both definition styles, as today.** Decorated classes by default (NTS-583), map schemas alongside. `--labels` scopes the run; adopting into a codebase that already declares some models means generating to a scratch directory and hand-carrying — acceptable at scaffold frequency.
- **Fresh-DB bootstrap is the contract to fix.** The round-trip claim should be strengthened from "no drift against the introspected database" to "generate → `installSchema()` on an empty database reproduces the source graph's constraints" — that is the acceptance test for the fidelity work.

## 6. Recommendation for 1.x

Adopt approach (a) + the Ontology Graph Spec mapper from (c); refuse (b) and the rest of (c) for now. Sized **M** overall, split as three follow-ups:

1. **[NTS-681] Emit `unique`/`exists`/`index` flags from installed constraints in `generateModels()`** — S. Acceptance criteria:
   - A generated model's unique-constraint property carries `unique: true` (alongside `primary: true`) iff the installed constraint's name equals `schemaObjectName(label, [key], UNIQUE)`; same guard for range indexes → `index: true`.
   - On an Enterprise connection, an `IS NOT NULL` constraint on `(label, key)` emits `exists: true`; Community emits nothing (edition detected as in `inspectSchema`, NTS-598).
   - New integration test: seed a graph with constraints → generate → register → `installSchema()` on a **fresh** database → `schemaDiff()` clean on the generated labels; hand-named constraints still generate no flags and produce no second constraint on apply.
2. **[NTS-683] Map Neo4j Ontology Graph Spec documents to neode model definitions** — M. Acceptance criteria:
   - Pure exported mapper (name TBD, e.g. `ontologySpecToSchemas()`) from the spec's decoded `GraphModel` to `Record<string, SchemaDefinition>`: nodes → models (label, description, properties with type/unique/must_exist → `required`), relationships → relationship entries with direction from `from`/`to`, constraint/index entries mapped where neode supports them.
   - `@neo4j/ontology-graph-spec` is a devDependency used in tests only; neode's runtime gains no dependency.
   - Mapping table documented (spec field → neode field → dropped fields with reasons), unit tests over the spec's example movies document, and the mapper output round-trips through `defineModel()` + `installSchema()` without drift.
3. **[NTS-682] Document `neode-generate` and `generateModels()`** — S. Acceptance criteria: user docs (agent docs + README section) cover the CLI flags, both output styles, the fidelity limits of §2 (so the hand-corrections are expected), and the scaffold-then-drift-check workflow. No changeset-style API change.

**Explicitly NOT doing in 1.x:** RDF/OWL or neosemantics import (no demand signal; a modelling project of its own); incoming/`BOTH` direction inference and writable-relationship emission (app intent, not introspectable); int/float disambiguation via property-type constraints and truncation warnings (worth doing opportunistically inside NTS-681 but not gating); live/continuous import or automatic merge into existing definitions (unsafe per the comparable-tools record); importers for other OGM formats; a third definition style; APOC dependence.

Once the three follow-ups land, the decision worth promoting to a numbered ADR (`docs/decisions/`, the house pattern) is the one-shot merge semantics and the two-styles-only import rule; this report is deliberately filed under `docs/investigations/` so it does not squat an ADR number.
