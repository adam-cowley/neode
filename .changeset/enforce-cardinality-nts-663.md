DB-enforced inverse cardinality: relationships declare `enforce: '<uniquePropertyOnTarget>'` (NTS-663) and neode's write paths keep that `@Unique` target property pointed at the source node's primary-key value — "relate = claim". The target model's uniqueness constraint (installed by `installSchema()`) then rejects a second node claiming the same target at the database level, raw Cypher included, closing the inverse-side gap of the NTS-161 cardinality guard. `onClaimed` picks the conflict policy when the target is already claimed by a different source: `'refuse'` (default — relate() matches zero rows and resolves `undefined`), `'detach'` (the other claimant's edges are deleted in the same statement and the claim moves) or `'throw'` (NeodeError naming the current claimant). `replaceRelationship()` / `syncEdges()` move the claim in their single atomic statement (REMOVE on the detached targets, SET on the new ones); `delete()` / `deleteAll()` release the claims of the nodes they remove. The declaration is validated when the relationship is first written: the named property must exist on the target and be `@Unique`, and cardinality must be `one` / `zeroOrOne` (`many` + `enforce` throws). Residual: the forward side (one target per source) stays an application-level guard — Neo4j has no edge-count constraint, so concurrent first-claims onto different targets are not DB-prevented.
