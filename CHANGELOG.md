# neode

## 1.0.0-next.2

### Major Changes

- bb9df12: 1.0 API sweep (NTS-670): the deprecated `@String` decorator is removed — declare string properties with `@Property({ type: 'string' })`. `@String` shadowed the global `String` type, which is why `@Property` was always the recommended form. The `setDeprecationWarnings()` export went with it: `@String` was the only deprecated surface left, so the NTS-163 warning machinery has nothing left to warn about. With this change no `@deprecated` surface ships in the stable major.

### Minor Changes

- 7b855df: Agent-readable docs: per-page markdown under docs/agent/ linked from llms.txt, an installable skills pack (skills/neode/SKILL.md), runtime deprecation warnings naming the replacement (@String), and the generated docs in the published package files.
- d0b0b88: Ambient transactions: `neode.transaction(callback, { routing?, database?, retries? })` binds the open transaction to AsyncLocalStorage, so facade/repository calls inside the callback join it without threading a handle — nested calls join the outer transaction, and a failure classified as transient (`TransientError`) retries the whole callback in a fresh transaction, so the callback must be idempotent. Requires a runtime with AsyncLocalStorage; the explicit-handle and managed APIs are unchanged for runtimes without it.
- d103009: Delete semantics tightened (NTS-595): `delete()` now cascades only into relationships explicitly annotated `cascade: true` — un-annotated relationships are detached, not deleted, so their targets survive (pass `{ cascade: true }` for the old delete-everything behaviour); the self-referential cascade walk is capped by the exported `MAX_CASCADE_DEPTH` (10, overridable per call with the `depth` option); `@SoftDelete` deletes are node-only and idempotent (a repeat soft delete never re-stamps `deletedAt`); and `deleteAll()` without filters is refused with a fix hint unless confirmed with `{ all: true }` (NTS-578 destructive-guard precedent). The cascade statement also no longer cross-multiplies rows across sibling cascade segments.
- ebb2a4c: `applySchemaDrift()` accepts `returnDriftAfter: true` to run one post-apply inspection pass and return `{ statements, driftAfter }` instead of the bare `SchemaResult[]` (NTS-659) — one probe serves apply + verification, so drift-repair callers no longer need a second `schemaDrift()` after applying. Opt-in: without the flag the return shape is unchanged.
- f31656f: Batch import story (NTS-625): new `neode.rowToProperties(Model, row, { map? })` (also exported as a standalone `rowToProperties(schema, row, options)`) maps one source row — a CSV / JSON / NDJSON record — to the property map `createMany()` / `mergeMany()` take: header renames via `map`, defaults, fakes, transforms, then type conversion through the model schema before validation. Non-throwing: returns `{ ok: true, properties }` or `{ ok: false, errors: ValidationIssue[] }` (every failing check for rule violations; one issue for values the type cannot absorb, such as nested relationship rows). Streaming import needs no new API: parse at the edge with any reader and feed batches of mapped rows to `mergeMany()` — `for await` gives backpressure and each batch commits its own transaction; merges on the model's merge fields keep re-runs idempotent. Recipe: `examples/cookbook/bulk-import.ts`.
- 9f20305: `BoundBuilder` read terminals for the one-row shape (NTS-613): `.first()` builds and runs the statement routed READ and resolves the first `QueryRecord` — undefined when the result set is empty — and `.scalar(name)` narrows that first row to one named column's value (undefined on an empty result). Replaces the `rows.records[0]?.get('…')` pattern at raw-read call sites; caller parameters merge over the builder's own params like the other terminals.
- 0d2adb0: Negative pattern predicate on the Builder (NTS-657): `whereNotPattern(alias, type, direction?)` renders `WHERE NOT (alias)<-[:TYPE]-()` — "node with no such relationship" as a typed pattern predicate, the supported replacement for raw `whereRaw('NOT (…)-[:TYPE]-()')` strings and for the OPTIONAL MATCH + IS NULL idiom that silently mis-filters on the embedded engine.
- 3d80bf3: Builder path patterns (NTS-658): `shortestPath(variable, from, to, { relationship?, direction?, degrees? })` renders `MATCH p = shortestPath((a)-[:TYPE]-(b))` legs for path-finding reads — traversal bounds use the Neo4j-legal `'..N'` / `'1..N'` forms (an exact minimum like `2` throws naming the fix, and the pinned multi-hop pattern stays expressible through match()/relationship()/to()/asPath()) — and `expr` gains `nodes()`, `relationships()` and `type()` helpers so path variables project in RETURN (`[n IN expr.nodes('p') | n.name]`).
- 9a6dd0b: Builder: property-to-property comparison predicates — `whereProps(left, operator, right)` compares two references (`alias` or `alias.property`, quoted identifiers, never parameters) and `whereInRefs(property, listRef)` tests membership against a collected list, both validated against the comparison-operator set and composable with `or()` / `whereGroup()`, so ref-to-ref predicates (`p.unitsInStock <= p.reorderLevel`, `other <> c`) no longer need `whereRaw` hand-strings.
- 3957f31: feat(bulk): report per-row fate when a chunk fails (NTS-649)
  
  `createMany()` / `mergeMany()` now throw a `BulkChunkError` when a chunk's UNWIND fails: it carries `chunkIndex` and `failedRows` — each failing row's index in the full input plus its own error, found by re-running the chunk's rows one transaction per row with every diagnostic transaction rolled back (nothing the diagnosis touches commits). Every row of the failed chunk is unwritten — valid rows included — while earlier chunks stay committed; rows that only fail together (e.g. duplicate unique values within a chunk) report an empty `failedRows` with the reason in the message.
- 3c501e6: Bulk relationship merging: `neode.relateMany(Entity, key, rows)` — the edge-writing counterpart of `mergeMany()`. Rows name the from- and to-nodes by primary-key value (`{ from, to, properties? }`), one UNWIND statement per chunk matches both endpoints and MERGEs the edge, so re-running the same rows never duplicates a relationship (relate()'s idempotency, per pair). Edge properties apply whether the MERGE created or matched the edge — the map-granularity form of relate()'s ON CREATE SET / ON MATCH SET (NTS-628) — and convert + validate through the shared edge-property pipeline (NTS-509/628). Restricted cardinalities (`one` / `zeroOrOne`) and edge-entity targets are rejected: use relate() per pair for those. Built for the JobStash acceptance harness's ingest path, where relationship rows arrive as ID pairs from CSV/JSON imports.
- 7bb6c84: Composite index declarations (NTS-650): `index: ['a', 'b']` on a model property declares one range index over N properties — created by `installSchema()`, detected and repaired by `schemaDrift()` / `applySchemaDrift()` — and the docs note Neo4j's limits: uniqueness constraints are single-property, node key constraints are the Enterprise composite analogue.
- e742194: Curate the public export set (NTS-600): the package root now exports exactly the documented API — the `Neode` facade, decorators, `Repository`, `Builder`, map-API config helpers, the typed error taxonomy and the functions the guides teach — while everything else (graph-type and model-generation machinery, load-spec plumbing, registry/service internals, never-documented option types) moves to an in-repo internal module and out of the type surface; the pre-1.0 type surface narrowed to the documented API. Runtime behaviour is unchanged.
- 806a2ab: Descriptive, fix-suggesting errors everywhere (NTS-442 — house rule): every error the library throws is a `NeodeError` naming what failed, where, why, and the suggested fix — unknown property/relationship keys suggest the closest declared name ("did you mean") and list the defined ones, connect failures carry the connection-config fix, unique violations name the fix (`merge()` or change the value), and all remaining bare `Error` throws are typed. Driver failures keep carrying the failing statement with REDACTED parameters (keys and shapes, never values).
- 7ac7441: Guard the destructive schema operations (NTS-578). **BREAKING:**
  
  - `wipe()` now refuses to run unless called with `{ confirm: true }` (or with `NEODE_ALLOW_WIPE=true` set suite-wide). It also refuses a non-local `uri` (option, or `NEO4J_URI`) unless `allowRemote: true`, and verifies the connected database name when `database` is given. Add `{ confirm: true }` to existing `wipe(...)` calls. It deletes in batches (`CALL { } IN TRANSACTIONS`, falling back to a bounded `LIMIT` loop), only tolerates "unsupported syntax" errors (authentication and other failures now throw), and returns a `WipeReport` (nodes deleted, graph type reset, dropped and failed constraints/indexes) instead of `void`.
  - `installGraphType()` / `GraphTypeService.create()` no longer replaces the server's whole graph type: by default it only `ADD`s the missing element types and constraint items and reports differing definitions as failed results, leaving other applications' objects on a shared database alone. The old `ALTER CURRENT GRAPH TYPE SET` behaviour is opt-in with `replace: true`, which is refused when it would drop objects no registered model declares unless `canDropUndeclared: true` is also passed. The default statement is now `ALTER CURRENT GRAPH TYPE ADD { ... }`.
  - `dropSchema()`, `dropGraphType()` and `applySchemaDiff()` docs now state that they act on the connected database.
- 63588be: **Eager relationship creation on the write path (NTS-615)**: `create()` and `update()` accept an options object with a `relate` map — relationship key to saved target entity (or array of targets) — and relate them inside the same managed transaction as the write:
  
  ```ts
  await db.create(TrailEvent, { ...props }, {
    relate: { tenant: tenantNode, submission: submissionNode },
  })
  ```
  
  One transaction, atomic from the caller's view: a failure mid-write rolls the node and its edges back together, so no orphan nodes. Edges are MERGE-based, so retries stay idempotent (the same guarantee `relate()` gives); cardinality is guarded per edge. The legacy `database` string third argument keeps working on both methods.
- 26a9900: DB-enforced inverse cardinality: relationships declare `enforce: '<uniquePropertyOnTarget>'` (NTS-663) and neode's write paths keep that `@Unique` target property pointed at the source node's primary-key value — "relate = claim". The target model's uniqueness constraint (installed by `installSchema()`) then rejects a second node claiming the same target at the database level, raw Cypher included, closing the inverse-side gap of the NTS-161 cardinality guard. `claimConflict` picks the conflict policy when the target is already claimed by a different source: `'refuse'` (default — relate() matches zero rows and resolves `undefined`), `'detach'` (the other claimant's edges are deleted in the same statement and the claim moves) or `'throw'` (NeodeError naming the current claimant). `replaceRelationship()` / `syncEdges()` move the claim in their single atomic statement (REMOVE on the detached targets, SET on the new ones); `delete()` / `deleteAll()` release the claims of the nodes they remove. The declaration is validated when the relationship is first written: the named property must exist on the target and be `@Unique`, and cardinality must be `one` / `zeroOrOne` (`many` + `enforce` throws). Residual: the forward side (one target per source) stays an application-level guard — Neo4j has no edge-count constraint, so concurrent first-claims onto different targets are not DB-prevented.
- 025bffc: `extendGraphType()` / `alterGraphType()` (NTS-551): the two remaining graph type verbs — `ALTER CURRENT GRAPH TYPE ADD` adds new element types and constraint items to the installed graph type (only additions are valid server-side), and `ALTER CURRENT GRAPH TYPE ALTER` redefines existing element types. `alterGraphType()` defaults to the model-derived element types with their uniqueness stripped: key/uniqueness constraints cannot be altered and remain unchanged server-side (passing a definition that still carries them throws). Exports `graphTypeAddStatement()`, `graphTypeAlterStatement()` and `deriveGraphTypeElementsOnly()`.
- 025bffc: Composite `REQUIRE` constraints in derived graph types (NTS-552): a property declared with `unique: ['a', 'b']` derives a named `REQUIRE (n.a, n.b) IS UNIQUE` item, and `index: ['a', 'b']` derives `IS KEY` — a graph type enforces rather than indexes, and key (existence + uniqueness) is the strongest composite constraint. Groups are deduplicated per property list (the flags may be declared on more than one of the group's properties) and work on relationship element types from the `@RelationshipEntity`'s properties too.
- 025bffc: Graph type drift as a first-class schema family (NTS-550): `schemaDrift()` probes `SHOW CURRENT GRAPH TYPE` and diffs the installed canonical specification against the model-derived definition per element — missing element types report an `ALTER CURRENT GRAPH TYPE ADD` fix, stale ones an `ALTER CURRENT GRAPH TYPE DROP`, redefined ones an `ALTER CURRENT GRAPH TYPE ALTER` — and `formatSchemaDrift()` renders the family. On backends without graph type support the family is omitted (drift stays cheap and never-throws). `wipe()` now resets the graph type to empty first (`ALTER CURRENT GRAPH TYPE SET { }`, best-effort): graph-type-derived constraints only go with the type. Exports `parseGraphTypeSpecification()` and `currentGraphType()`.
- 025bffc: Named graph type constraints (NTS-549): derived uniqueness is hoisted out of the element type property maps into explicitly named `CONSTRAINT <label>_<prop>_unique FOR (n:<Label>) REQUIRE (n.<prop>) IS UNIQUE` items, so the constraint name is addressable in `DROP CONSTRAINT` / `ALTER CURRENT GRAPH TYPE DROP` (inline `IS UNIQUE` was only ever nameable by server-generated names, and dropping an element type leaves its uniqueness constraints behind). `dropGraphType()` now also drops the named items. `installGraphType()`/`dropGraphType()` accept `{ constraints: [...] }` for constraints on labels/types that are not identifying ones — derivation cannot produce those, and it is the only spelling for property existence/type constraints on non-identifying labels. Exports `GraphTypeConstraintDefinition`, `GraphTypeConstraintKind`, `graphTypeConstraintName`.
- 6be5967: Instance relationship query builder: `instance.related(key)` composes Builder-style verbs (where / orderBy / limit / skip) on top of one declared relationship traversal, with the terminal `find()` / `first()` / `count()` running it and hydrating the related entities through the regular hydration path. The related target's own global filters apply inside the traversal read — a filtered-out target yields an empty result, never an error (plain MATCH, no OPTIONAL MATCH). The scope's target type narrows from the relationship declaration.
- f5b7a30: Document the kNN top-k-before-filter pitfall — a filtered search can return fewer than the requested limit — with the over-fetch + post-filter workaround (NTS-438).
- 35e3c8a: instance.load(key, { order, limit, skip }) lazy-loads one relationship in place (NTS-558)
- fd30993: Facade methods called inside the managed `inReadTransaction()` / `inWriteTransaction()` callbacks now JOIN the unit's transaction (NTS-642) — `neode.cypher()`, `neode.create()`, `neode.save()` and friends run on the same transaction and commit or roll back with it, on every backend. Previously they fell through to autocommit: silently outside the unit on Bolt, and a deadlock (or a 30s queue timeout, NTS-576) on the embedded Relate engine's single transaction slot. A statement that failed on the driver and was swallowed inside the callback now refuses the unit's commit with a descriptive `NeodeError` (the NTS-589 rollback-only marker, applied to the managed units too) instead of surfacing the server's commit refusal. The managed units still never retry; the close endpoints and nested-join semantics of the callback's `tx` are unchanged.
- 5698257: Named read filters now compose beyond the standard read paths (NTS-614): `Builder#withFilters(model, alias?, options?)` appends a registered model's declared filter fragments (soft delete included) into the current WHERE segment and merges the filters' params, and `readFilterFragment()` with `ReadFilterOptions` is exported from the package root for hand-written Cypher.
- 3717970: Named global filters with pattern-comprehension relations (NTS-162): `@Filter({ name, where, default })` declares named read filters on a model, `setFilterParams(name, value)` parameterises them, and every standard read (find / get / all / paginate / findManyAndCount / lazy / chunk / search / knn / projections / eager loads / repository reads) composes them from one central place in the query services. `{ withoutFilters: ['name'] }` (or the reserved `'*'`) disables filters per query — each name independent, with the built-in @SoftDelete filter addressable as `softDelete` and `includeDeleted` still honoured. Filtered relations render the target model's filters as a WHERE inside the relation's pattern comprehension (or the `with` load spec's COLLECT subquery) — a filtered-out target simply doesn't match, the relation reads as absent (`[]`) and the parent row survives; never OPTIONAL MATCH. Soft delete composes as a label predicate (labels-as-state, NTS-128). Documented and tested bypasses: raw Cypher (readCypher/writeCypher/cypher), hand-built Builders, and bulk writes (deleteAll, and the write paths' internal re-hydration, which use the `'*'` bypass).

- 760ad3b: Strict relation access (NTS-155): hydrated entities now guard relationship properties that the load did not request — reading one throws `RelationNotLoadedError` (naming the `with` load-spec fix and `instance.load(...)`) when `setStrictRelationAccess(true)` is on, and returns `undefined` otherwise (the default, so existing neode-style code is unaffected until the switch is flipped). Loaded-and-empty relationships (`[]` for many, `undefined` for a singular match miss) stay readable in strict mode; static `eager` relationships always count as loaded. Works for decorator and map-defined models.
- dca83d5: Instance dirty tracking with partial SET (NTS-157): hydrated entities snapshot their persisted scalar property values, and `save()` / instance `update()` write only what changed — a clean instance saves as a no-op (no query, no lifecycle events), and a dirty one emits a partial SET carrying the dirty keys only. New Eloquent-style instance methods `isDirty(key?)`, `getDirty()` and `wasChanged(key?)` report pending and last-written changes. Dirty saves never walk the graph (relationships stay on the explicit relate/detach paths), the primary key is treated as identity rather than state, and projected read-model properties are never written.
- db9d055: Adds `@Version()` for optimistic locking (and the matching `version` config option on `@Property` / `@Property()` configs and the map API). A created node starts at version 0 and every write addressed to that node increments it by exactly 1 — a clean no-op save (NTS-157 dirty tracking) never bumps it, and version never cascades to related nodes reached through another node's save. Writes on an instance carrying the version it was hydrated with (`update()`, instance `save()`) add `WHERE n.version = $expected`; when zero rows match — the node was modified or deleted by another transaction — a typed `OptimisticLockError` (extending `NeodeError`, stable `name`, never classified as a transient retry) is thrown with guidance to reload and retry. `mergeOn()` maintains the counter but carries no expected version to guard; bulk `createMany` stamps created rows with 0 (explicit row values win) and `mergeMany` additionally bumps matched rows.
- c2ae2a5: Relationship write-time cardinality (`one` / `zeroOrOne` / `many`) and `syncEdges()` (NTS-161)
- ca20e98: Database introspector: generate entity models from an existing graph — `neode.generateModels()` (and the `neode-generate` CLI) walk node labels, sample property values to infer types (absent properties optional, conflicting types a descriptive error), suggest the unique constraint's property as the primary key, and emit both decorated classes and map schemas without re-declaring constraints or indexes, so the generated models round-trip through `installSchema()` with no drift.
- a4992ba: Adds `@CreatedAt()` and `@UpdatedAt()` property decorators (and the matching `createdAt` / `updatedAt` config options on `@Property` and the map API). Both are stamped server-side with `datetime()` so clocks never drift across clients: `@CreatedAt` is written once on create, `@UpdatedAt` on create and on every write (`update()`, `save()`, `mergeOn()`, bulk `createMany` / `mergeMany`). `@CreatedAt` properties are never rewritten by `update()`, and a no-op save on a clean tracked instance (NTS-157) touches neither timestamp — giving `paginate()`'s default `createdAt` keyset a property that is actually maintained.
- b75440b: Pagination extras (NTS-166): `neode.findManyAndCount(model, filter, options?)` returns every matching entity with its total in one call (`{ items, total }` — options trim the data read only, `total` always counts the whole filter); `neode.chunk(model, filter, size, callback, options?)` walks a large read in keyset pages, handing the callback each chunk in order (return false from the callback to stop early) and resolving to the number of items delivered; `neode.lazy(model, filter, options?)` is an async iterator over the same keyset walk, yielding one entity at a time so memory stays flat on large reads — breaking out of the `for await` loop stops the walk cleanly, with no session left open. Both walks default to keying on `createdAt`; pass `orderBy` to key on another property.
- 199670a: Factories and seeders for entities (NTS-167): `FactoryBuilder.make(overrides)` builds unsaved instances with the same override > default > fake precedence as create; `FactoryBuilder.has(otherFactory, relationshipName)` composes another factory onto every created instance through the explicit relate path; a `Seeder` base class plus `runSeeders()` runner for idempotent seeding via `neode.mergeOn` (reruns update instead of duplicating); and `seededRandom(seed)`, a deterministic PRNG for reproducible fixtures inside `fake` generators.
- 2f26f03: Dirty-aware embedding recompute: on a tracked save (`save()` on a hydrated entity), a vector property declared with `from` + `provider` recomputes its embedding only when the source property is dirty — a clean source keeps its stored vector and costs no provider call, a dirty vector the user set explicitly still wins, and the freshly computed vector is persisted even though the instance itself did not change it (previously the stale stored embedding was silently kept).
- f91e27f: Builder gains `existsExpr(build, imports?)`: the `EXISTS { … }` subquery as a composable expression for the positions `whereExistsSubquery` cannot reach — nested inside `or()` chains (`or(builder.existsExpr(…))`), negated (`` `NOT ${builder.existsExpr(…)}` ``) and projected in RETURN. Sub-query values bind as parameters and namespace (`sub0_`…) exactly like the clause form, and unbound `$references` fail fast at build time. `whereExistsSubquery` is now a thin wrapper over the new method (NTS-465).
- d4c979d: Builder gains full-text index DDL builders — `createFulltextIndex(label, properties)` and `dropFulltextIndex(label, properties)` — so schema DDL composes like queries through the same statement builders the SchemaService uses, alongside the existing constraint/index builders. Every DDL builder emits idempotent `IF NOT EXISTS` / `IF EXISTS` statements, unblocking callers that install per-instance schema (NTS-173).
- 8719843: Direction BOTH is now an undirected match: relationship patterns render `-[:TYPE]-` (no arrows), matching relationships of the type in either direction. Write paths (relate, create, save) reject BOTH with a descriptive error — undirected relationships are match-only, since Neo4j cannot create one; set direction OUTGOING or INCOMING to write (NTS-483).
- 181dd95: Adds model observers (NTS-511): `neode.observe(Model, { beforeSave, afterSave, beforeDelete, afterDelete })` — typed lifecycle hooks composed over the write paths of both scopes (facade and open transactions). `beforeSave` runs inside the write before the dirty diff (mutations count; an error fails the write and rolls the transaction back), `beforeDelete` can block a delete, `afterSave`/`afterDelete` run after hydration with `{ isNew, database }` context. Returns the off function.
- c3ab9c5: `@RelatedOne` / `@RelatedMany` accept a `path` — an array of `{ type, direction?, target? }` hops — for declarative multi-hop reads: the hops are chained in one pattern comprehension and the last hop ends at the projected node (`target()` label-filters it and type-checks `fields`; intermediate hops label-filter only when they declare a `target`). `fields` is required with `path` (projected form only). An optional `where` fragment filters elements inside the comprehension (`node` = final node, `this` = the annotated node). End nodes reached through several paths are deduplicated on hydration, so a two-hop "co-purchased products" projection lists each product once.
- c3ab9c5: Aggregate mode for typed traversals: `neode.traverse(...)` gains `.exclude(from, type, to)` (`WHERE NOT (from)-[:TYPE]->(to)`), `.groupBy(...aliases)`, `.countDistinct(alias, as)`, `.orderBy(field, order?)` and `.limit(n)`, plus `runAggregates()` — returning one row per group with the group aliases hydrated and the distinct count as a number. This is the co-purchase shape (entities reached through shared origins, ranked by how many origins they share, excluding ones already connected to the start). `run()` keeps its path-row shape; the two modes do not mix.
- e75279b: Build-and-run sugar on every scope (NTS-553): `neode.read(builder)` / `neode.write(builder)` build a `Builder` once and run it through `readCypher`/`writeCypher` (READ/WRITE routing), while `neode.read('MATCH …')` passes a raw string straight through. Caller-supplied parameters merge over the builder's own params. Mirrored on the `INeode` interface, so `tx.read(...)` / `tx.write(...)` inside `inWriteTransaction` run in the transaction's scope.
- e75279b: Fluent build-and-run chains (NTS-554): `neode.query()` now returns a `BoundBuilder` — a `Builder` bound to the instance (everything the plain Builder has, plus `.read()` / `.write()` terminals that build-and-run through `Neode#read`/`Neode#write` with READ/WRITE routing), so a whole query reads as one chain: `await neode.query().match('o', 'Order').… .return('o', 'p').read()`. `tx.query()` does the same inside an open transaction, running in scope. A `database` argument on `query()` is forwarded to the terminals. The standalone `Builder` gains no implicit execution.
- 6b7e3e8: Hydrate option on `neode.read()` / `neode.write()` (NTS-559): pass an options object — `{ hydrate: Model, alias?: 'o', database? }` — as the second argument (when there are no parameters) or the third, and the rows come back as hydrated entities of that class instead of raw records, the same overload shape `cypher()` offers. A Builder traversal that should return entities no longer needs the separate `hydrate()` call. Mirrored on the `INeode` interface and `TransactionalService` (in-transaction scope; the transaction mirrors take no `database`). The NTS-553 positional `(parameters, database)` shape is unchanged.
- b57e1b6: Load spec — the `with` option on find / findAll / all (NTS-560): request a non-eager relationship in a specific read, with per-relation query control, in one statement. `neode.find(Customer, id, { with: { orders: (relation) => relation.orderBy('orderDate', 'DESC').limit(20) } })` returns the customer with exactly the newest-20 orders hydrated; `with: { orders: true }` loads them all. The relation callback receives a restricted view (`where` / `orderBy` / `limit` / `skip` — bare property names, no return/writes/segments); unknown keys are rejected at compile time when the model type is known and throw a NeodeError naming the model and key at runtime. Requested keys materialize as own properties through the regular eager hydration path, so they count as loaded for strict relation access (loaded-and-empty renders `[]`).
  
  Deviation from the pattern-comprehension sketch: a decorated relation renders as a per-relation `CALL { WITH this MATCH (this)-[...]-(node) … WITH node ORDER BY … SKIP/LIMIT RETURN collect(node { projection }) AS <key>_loaded }` subquery collected into the same RETURN — pattern comprehensions cannot carry ORDER BY / LIMIT. One statement and hydrated entities, as contracted. Flat relations to node models only: a callback on a relationship-entity target throws. `Builder` gains `withSkip()` to complete the NTS-477 WITH-carried trim.
- 24ba3e1: Managed transactions (NTS-561): `inReadTransaction()` / `inWriteTransaction()` now commit the transaction when the work resolves — a throw rolls back, as before. The caller no longer has to remember `tx.commit()`: an uncommitted callback no longer leaks an open transaction (which deadlocked the next write on the embedded engine's single-transaction connection). Migration note: an explicit `commit()` inside the callbacks is now optional (existing code keeps working — a second `commit()` is a no-op), a `rollback()` after a commit does nothing (the commit stands, so "committed then threw" no longer surfaces a rollback error), and committing after a rollback throws — a failed transaction cannot commit.
